# Recipes

Five recipes for adding content. Each says which files to touch, in order, and which real file to copy. Read `ROUTER.md` first to see where things live and `EXTENSION POINTS.md` for the registration calls. Two example addons in `src/packs/_template/` (not shipped): `lantern.ts` is the R9 proof piece, one file with a vertex piece, its button, spots, shape, score and bot goal (`tests/lantern.test.ts`): copy it for a new piece. `demo.ts` holds a piece, action, tech node, client data function and bot goal stub (`tests/template.test.ts`): copy it, rename, delete what you do not need.

Checked against the code: the pack side (`registry.ts`, `addons.ts`, `harbor.ts`, `ricketyBridges.ts`, `tech.ts`) and the server glue (`socket.ts`, `view.ts`), all opened. Also checked in the 2026-10-31 trial: `client/render/board.ts`, `overlay.ts`, `index.ts`, `client/main.ts`, `actions.ts`, `store.ts`, `types.ts`. Not opened, so search before trusting them: shapes in `client/icons.ts`, `public/index.html`, and the DLC card list in `client/render/setup.ts`. Each recipe marks these. Notes ending "Until R8" describe hand-written glue that the rework removes; delete each note when its chunk lands.

After every recipe: `npm run addons` (when adding or changing an addon), `npm run headers:write`, `npm run index`, `npm run typecheck`, `npm test`. A new addon must not change a game it is not part of, so `tests/golden.snapshot.json` stays untouched.

## 1. New piece

A piece is a vertex or edge thing a player builds with the base `build` action.

1. **Define it** in the addon file (`packs/<dlc>/<addon>.ts`): a `PieceDef` with `id`, `target` (`'vertex'` or `'edge'`), `cost`, `vp`, `produces` (0 unless it makes cards), and `canPlace(ctx, pid, loc, mode)`. `canPlace` is geometry and ownership only; the `build` action checks price and supply. Gate it with a tech inside `canPlace` using `techGate`. An edge piece that continues roads sets `roadLike: true`. Copy: `lanternPiece` in `_template/lantern.ts` (vertex), `ricketyPiece` in `tidebound/ricketyBridges.ts` (edge).
2. **Give it a supply**: in the addon's `rules`, `pieceLimits: { [PIECE_ID]: n }` (this is how `rickety_bridge` and the template beacon get one; I did not read the code that turns it into `p.pieces`, so check a new piece's supply in the test). Add `baseLimit` on the def if the next piece should cost double past a number, and `scaleWithRadius: true` if the supply grows with the board.
3. **Register it**: `api.piece(def)` inside `register`. Prices always go through `priceOf` (`shared/pricing.ts`), so `COST_MODS` apply. Damage and repair: add a `DURABILITY_DEFS` entry (`ricketyDurability`).
4. **Look and click (no glue)**: add `visual` to the `PieceDef` (`PieceVisual`, `shared/visual.ts`): `slot` (`vertex`, `edge` or `edge:ocean`), `button` (`label`, `icon`, `order`, optional `group`), `hints` (`noSupply`, `cannotAfford`, `noSpots`) and `shape` (an SVG fragment using `{color}` and `{dark}`; a vertex shape is drawn around (0,0) inside a 12 px box, an edge shape along x from -50 to 50). The server sends it in the `visuals` event; the client draws the build button, supply badge, price popup, spot markers and placed shape from it and emits `place` `{ code, piece, loc }`, which `server/socket.ts` runs as `build` (the engine's refusal reason goes back). The per-player data `pieces[id] = { left, cost, spots }` comes from the generic `base.pieces_view`; the spots are the locations where the `build` action's `validate` passes, so there is no spots function and no `VIEW_DATA` entry. A tech-gated piece sets `available: (g, pid) => techGate(g, pid, TECH_X)` on its `PieceDef` and is then absent from `pieces` until unlocked. `registryVisualProblems` (run by the manifest tests) flags unsafe or non-JSON visuals. Copy: `_template/lantern.ts`. An edge piece uses the same fields; the lantern is the only piece proven so far.
5. **Do not copy the hand-written pieces' glue.** The net, harbor, feed and bridge buttons still have per-piece code (a `renderAll` block in `client/render/index.ts`, a button in `public/index.html`, a branch in `client/render/board.ts`, a shape in `client/icons.ts`); R8.8 migrates them one by one and deletes it. A piece with no `visual` still builds through `place`, but the client draws no button for it.
6. **Bot**: a `BOT_GOALS` entry whose goal action is `{ type: 'build', payload: { piece, loc } }` (`lanternBotGoal` in `_template/lantern.ts`, `ricketyBotGoal`).
7. **Test**: copy `tests/lantern.test.ts` (it builds a game with `makeGame`, checks the manifest, `pieces[id]`, a build through `dispatch`, the score and the bot); also test that nothing registers with the addon off.

## 2. New action

1. **Define it**: an `ActionDef` in the addon file with `type`, `validate(ctx, pid, payload)` returning an error string or `null`, `apply(ctx, pid, payload)`, and `legal(ctx, pid)` returning candidate payloads. `legal` must not use the RNG; the engine filters its output through `validate`. Use `getPlayer`, `canAfford`, `payToBank(ctx, p, cost)`, `ctx.emit(name, data)` and `ctx.log(text, color)`. For a cost that modifiers may change, use `priceOfUpgrade` (`harborUpgradeCost`). Copy: `upgradeHarborAction` in `tidebound/harbor.ts`, `tipBeaconAction` in `_template/demo.ts`.
2. **Register it**: in `register`, `api.action(def)` then `api.phaseAction('main', type)` (or another existing phase). `createRegistry` throws if a phase lists an unknown action.
3. **Server glue**: none. `server/socket.ts` has one generic `act` event: the client emits `socket.emit('act', { code: state.code, type: '<type>', payload })` and the engine runs it for this player (an unknown or illegal type is refused by `dispatch` and the reason goes back to the player). Treat the payload as untrusted: `validate` must check every field. No `socket.ts` edit, no event name.
4. **Client**: emit `act` as above (see `clickPirate` in `client/render/pirates.ts`, `clickHarborSpot` in `client/render/board.ts`). If the player needs legal spots or a price, register a `VIEW_DATA` entry as in recipe 1.
5. **Bot**: add an `actionScore` and/or a goal in a `BOT_GOALS` entry; without one, a bot picks the action only if its brain already scores it.
6. **Test**: `act(g, reg, 'a', type, payload)`; check `ok`, the error text, and that `JSON.stringify(g.rng)` is unchanged.

## 3. New addon

1. **Copy** `tidebound/harbor.ts` (complete and small) or `_template/demo.ts` to `packs/<dlc>/<name>.ts`.
2. **Fill the `AddonDef`**: `id` must start with `<packId>.`. `links` need 2 or more distinct `{ target, kind }` and at least one target from `GENERAL_SERVICE_IDS` (`shared/addons.ts`); targets that are not General services must be real addon ids. `deps` list addon ids that must be declared earlier. `rules` are defaults merged only while the addon is on. Everything else goes inside `register(api)`.
3. **Generate the pack's addon list**: run `npm run addons` to regenerate `packs/<dlc>/addons.generated.ts` in dependency order (`packs/<dlc>/index.ts` imports `addons.generated.ts`, so you never edit an `addons` array by hand; `tests/index.test.ts` fails if it is stale). Re-export anything the server or client imports from `packs/<dlc>/index.ts`.
4. **Client card list**: the DLC and addon cards in `client/render/setup.ts` have a built-in fallback list; its Tidebound ids must match the server's addon list (`mapOptionsView().addons`, checked by `tests/tidebound.test.ts`). The server's list comes from the registry (`server/mapmenu.ts`) with no edit.
5. **A new DLC pack** (not just an addon): a `Pack` with `deps: ['base']` and an `addons` list, added to `allPacks` in `packs/index.ts`. Not needed for a new addon inside an existing DLC.
6. **Test**: `auditAddons(allPacks)` returns `[]` (`tests/addons.test.ts`); with the DLC or the addon switched off nothing is registered (`{ dlc: { x: false } }`, `{ addons: { 'x.y': false } }`); with it on the content is there; zero `g.rng` draws.

## 4. New tech node

1. **Define it**: a `TechDef` in `packs/<dlc>/tech.ts` (`TIDEBOUND_TECH_DEFS`) or in the addon file: `id` `<packId>.<name>` (export it as a `TECH_...` constant), `name`, `branch`, `tier`, `path`, `prereq`, `costOffset`, `dlc`, `description`, optional `onUnlock(ctx, pid)` for a one-time effect. Copy a node from `tidebound/tech.ts`; the costs and layout rules are in `Tech Tree Design.md` and the cost formula is in `shared/stage1.ts`.
2. **Register it**: `api.define(TECH_DEFS, def)` from `register`. If several addons register the same list (as `registerTideboundTechs` does), give every def `replace: true` so repeats are harmless.
3. **Gate the feature** where it happens, with `techGate(g, pid, TECH_ID)` (true when `rules.techTreeOn` is off) or `hasTech(g, pid, TECH_ID)` (true only when owned). Put the gate in `canPlace`, in `validate`, in the `...SpotsView` function, and in `legal`; a gate in only one of them leaks.
4. **Effects**: a bonus inside an existing rule goes through the matching keyed registry (`COST_MODS`, `RATIO_MODS`, `DISCARD_LIMIT_MODS`, ...); extra VP through `api.hook('vp', ...)` (`grandCausewayVpHook`).
5. **Glue**: the tech panel is built from the registry rows (`techPanelFor`), so it needs no client edit. Extra VP in the breakdown: a `VIEW_DATA` entry with `vpBonus` (`grandCausewayViewData` in `tidebound/tech.ts`). A piece the tech unlocks: `PieceDef.available` (recipe 1).
6. **Test**: copy `tests/tideboundtech.test.ts`.

## 5. Client overlay or panel

Examples: the pirate layer (`client/render/pirates.ts`), the bridge picker (`client/render/bridgepicker.ts`), tile tints (`client/render/overlay.ts`).

1. **Data first (server)**: the addon exports a function `(g, reg) => data | null` that returns `null` when the addon is off or there is nothing to show (`pirateClientView`, `wreckClientView`, `tideClientView`). Register it in the addon's `register` as a `VIEW_DATA` entry (`api.define(VIEW_DATA, def)`, `ViewDataDef` in `shared/viewData.ts`; `server/view.ts` needs no edit): `shared: (g, reg) => ({ field })` for public data, `player: (g, reg, p, who) => ({ ... })` for per-viewer data (`who.self`, `who.over`, `who.spectator`; `pirateDrives`), `overlays: (g, reg) => ({ [hexId]: { kind } })` for tile tints, `vpBonus` for extra VP. Rules learned in R7a.5: (a) null versus undefined matters on the wire: a public field is `null` when its addon is off, a per-player field is `undefined`. An addon entry does not exist while the addon is off, so a public field that must be `null` when off needs a `null` default in an always-on pack-level entry (`tidebound.view_defaults` in `tidebound/index.ts`, priority below every addon entry, first wins). (b) A field the old code never gated by addon (`portLevels` reads the base port ladder, which a base tech also writes) is registered at pack level, in the pack's own `register` (`tidebound.port_levels`), not in an addon. (c) Per-player fields: recompute the old gate expression and `who.self` exactly, and keep `undefined` when off. Overlays: `overlays()` returning `undefined` or `null` means not taking part (the merged `hexOverlays` stays `null`), `{}` means taking part with nothing to show; when two entries set the same hex the higher `priority` (then the lower id) keeps it, because the client draws one overlay per hex. Test: inline-expect cases in `tests/viewState.test.ts` (addon off, tech missing, lobby) plus the snapshot for what a full game sends. The lobby (no game) does not read the registry: `view.ts` keeps a temporary `lobbyNulls` for the five moved public fields until R8.
2. **Own file** `client/render/<name>.ts`, copying `pirates.ts`: a `STYLE_ID` and an `ensure...Styles()` that adds a `<style>` once on first draw, a function returning an SVG or HTML string, and a click handler that emits `act` (`socket.emit('act', { code: state.code, type: '<action type>', payload })`, as `clickPirate` does). Guard clicks with `hasDraggedMap`.
3. **Wire it (search first)**: the board layer in `client/render/board.ts` (search `renderPiratesMarkup` and `boardPiratesLayer`; each layer is rewritten only when its markup changes); the file's click handler in the `Object.assign(window, ...)` block in `client/main.ts` when the markup uses inline `onclick`; the new state fields in `client/types.ts`. A new tile tint kind is not data: `HexOverlayKind`, `PATTERN_IDS` and `overlayPatternDefsMarkup` in `client/render/overlay.ts` are a closed list, so add the kind in all three, with a tint and a distinct pattern (colorblind rule, `Design UI Philosophy.md`). Until R8. A popup or panel not drawn on the board is called from `renderAll` in `client/render/index.ts`.
4. **Server event**: none needed. A click that triggers a game action emits `act` (recipe 2); one that builds a piece emits `place` (recipe 1).
5. **Test**: copy `tests/tideboundnetsclient.test.ts` (client-side tests exist for the net spots).
