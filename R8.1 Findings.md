## 5. `src/server/runtime.ts` — `gameRegistry` and `mapRegistryKey`

- **`registry` (`src/server/runtime.ts:9`)**: `export const registry = createRegistry(allPacks);` — a single shared base registry (with all DLCs off) created once at server startup.
- **`gameRegistry(rules)` (`src/server/runtime.ts:12–17`)**:
  - Checks whether `rules?.dlc` has any truthy value (`Object.values(rules.dlc).some(Boolean)`).
  - If no DLC is enabled, returns the shared `registry`.
  - If any DLC is enabled, calls `registryFor(allPacks, rules)` fresh (un-cached).
- **`mapRegistryKey(s)` (`src/server/runtime.ts:20–22`)**:
  - Calls `resolveAddons(allPacks, { dlc: s.dlc, addons: s.addons }).enabled`, sorts the enabled addon IDs alphabetically, and joins them with `','` (returns `''` when no addon is enabled).
- **`mapRegistryFor(s)` (`src/server/runtime.ts:32–42`)**:
  - Caches `registryFor(allPacks, { dlc: s.dlc, addons: s.addons })` in `mapRegistries` (`new Map<string, Registry>()`, capped at `MAP_REGISTRY_CACHE_MAX = 32` entries), keyed by `mapRegistryKey(s)`. When `key === ''`, returns `registry` without touching the cache.
- **Could the client be sent a registry-derived manifest per game?**
  - **Yes.** Both lobby settings (`room.settings.dlc`, `room.settings.addons`) and in-game rules (`room.game.rules.dlc`, `room.game.rules.addons`) have the exact `{ dlc, addons }` shape accepted by `mapRegistryKey` and `mapRegistryFor` / `gameRegistry`. Because the enabled addon set uniquely determines which `PieceDef`, `ActionDef`, and keyed registry entries are registered, a visual manifest derived from the registry is completely determined by `mapRegistryKey` and can be cached by that key and sent whenever a client's seen manifest key differs from the room's current key (both in the lobby and in a game; note that `syncMapOptions` in `src/server/net.ts` sets `optionsKey = null` when `room.game` is truthy, so a separate `visualsKey` or in-game manifest check is needed during a game).

## 9. Surprises (Contradictions with `Rework Progress.md` or `RECIPES.md`)

1. **`public/styles.css` does not exist; the stylesheet is `src/client/styles.css`, and `.bridge-upgrade-dot` is not in it.**
   - `Rework Progress.md` (R8.1, line 38) asks to read `public/styles.css` for `net-spot`, `fish-ring`, `bridge-upgrade-dot`, and `spot-pulse`. In the repo, the stylesheet is `src/client/styles.css` (copied to `dist/public/app.css` by `esbuild.config.mjs`), and `.bridge-upgrade-dot` is defined inside the inline `CSS` string in `src/client/render/bridgepicker.ts:34`, not in `src/client/styles.css`.
2. **`src/client/render/hand.ts` has per-piece recipe popup code omitted from R8.8's deletion list.**
   - `Rework Progress.md` R8.8 (lines 45, 49) lists `client/render/index.ts`, `board.ts`, `actions.ts`, `main.ts`, `types.ts`, `icons.ts`, `index.html`, and `view.ts`, but does not mention `src/client/render/hand.ts`. `hand.ts:13–79` hard-codes `'bridge'`, `'net'`, `'feed'`, and `'harbor'` in `RecipeKey`, `BUILD_RECIPES`, `renderRecipeStripHtml` (`me?.feedCost`, `me?.harborCost`, `me?.pieceCosts`), and `updateActionRecipePopups` (`#recipePopupBridge`, `#recipePopupNet`, `#recipePopupFeed`, `#recipePopupHarbor`).
3. **`PieceDef.icon` is completely unused.**
   - `Rework Progress.md` R8.1 asks how `PieceDef.icon` is used. Although `PieceDef.icon?: string` is declared in `src/shared/registry.ts:61` and set on pieces (e.g. `beaconPiece` in `src/packs/_template/demo.ts:78`), nothing in `src/client` or `src/shared` ever reads `PieceDef.icon`.
4. **`server/view.ts` still has `bridgesLeft: p.pieces.bridge ?? 0` in `enginePlayerView`.**
   - `RECIPES.md` and `Rework Progress.md` R7a state that all Tidebound per-player view fields moved to `VIEW_DATA` and only `bridgesLeft: 10` in `lobbyPlayerView` and `lobbyNulls` remained in `server/view.ts`. In fact, `enginePlayerView` at `src/server/view.ts:117` still hard-codes `bridgesLeft: p.pieces.bridge ?? 0` directly alongside `settlementsLeft`, `citiesLeft`, and `roadsLeft`.
